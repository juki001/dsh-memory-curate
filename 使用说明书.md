# dsh-memory-curate 使用说明书 / User Guide

> 中文在前，English follows. [Jump to the English guide ↓](#dsh-memory-curate-user-guide-english)

- 适用版本：0.3.x
- 适用对象：在 DeepSeek Harness（DSH）中使用长期记忆的普通用户
- 文档范围：功能介绍、使用方式、设置说明、常见问题。不涉及内部实现。

## 写在前面：你可能正遇到这些事

如果你用过带“记忆”的助手，下面这些抱怨大概不陌生。它们不是个别现象：公开社区里对记忆产品的讨论，最常提到的就是“跨会话失忆、压缩丢上下文、越存越乱、不可控、隐私、配置复杂”。这张表按困扰逐条对应本插件能做的事。

| 常见困扰 | 这个插件怎么处理 |
|---|---|
| 新开一个对话，它又把我的偏好、约定忘了 | 默认跨对话共享；新对话会带上一份轻量记忆摘要，完整内容按需取回 |
| 聊久了或压缩之后，它忘了我刚提的要求 | 最近 5 个“你亲自发出的回合”受保护；压缩前先确认关键内容已经记住 |
| 记忆越存越乱：重复、前后矛盾、过时信息混在一起 | 保存时提示可能重复；写入后给合并/冲突建议；支持重要程度和有效期 |
| 不知道它到底记了什么，想改也改不了 | 设置页可搜索、看来源和变更记录、编辑、删除 |
| 担心记忆被上传到云端，或者被不该看的人看到 | 记忆默认保存在本机；语义检索是可选功能，开启时会明确提示内容会发给所配置的服务 |
| 多个助手、多个项目互相串记忆 | 支持记忆分组和“共享 / 私有 / 开放”三种可见范围 |
| 配置太复杂，开箱不知道怎么用 | 默认零配置、关键词检索即可用；语义检索等高级项按需开启 |

一句话：**它是一个“不会失忆、也不会在压缩时把你刚说的话弄丢”的长期记忆插件**，同时把“记了什么、谁能看、怎么改”交回给你。

## 1. 这是什么

`dsh-memory-curate` 是一个长期记忆插件：让助手在不同对话之间记住你的偏好、约定、项目事实和重要决定，并在对话变长、上下文紧张时，优先保护最近的关键对话内容。

它主要做三件事：

- 让新对话接得上：偏好、约定、项目事实不用反复交代；
- 让压缩不丢重点：最近的关键要求不会被一起压掉；
- 让记忆可管：重复、过时、矛盾的内容能看见、能修改、能清理。

## 2. 适合记住什么

适合：

- 长期偏好：沟通语言、回答风格、常用工具、工作习惯；
- 稳定约定：默认使用什么命令、什么流程、什么命名方式；
- 项目事实：项目代号、模块职责、发布窗口、关键限制；
- 已确认的决定及其原因；
- 有时效的临时事实：例如“本周五前使用临时方案”。

不适合：

- 密码、API Key、令牌等敏感凭据；
- 大段原始日志、完整代码文件、一次性链接；
- 随时会变的临时状态（除非明确设置有效期）；
- 你不希望离开本机的私密内容（开启语义检索后，记忆正文会发送到你配置的检索服务）。

### 特别适合这些人

- 经常做跨天、跨周项目，不想每次重新交代背景的人；
- 同时使用多个助手或多个项目，需要把记忆分开的人；
- 被“聊久了就忘”“压缩后忘了刚才要求”坑过的人；
- 在意数据留在本机、希望记忆看得见改得动的人；
- 不想先折腾一套复杂记忆系统，想开箱即用的人。

## 3. 快速开始

1. **保存记忆**：在对话中自然说“记住……”“以后都……”“这个项目的约定是……”。助手会判断是否值得长期保存；也可以直接要求“把这条保存为长期记忆”。
2. **查看记忆**：打开 DSH 设置页，找到“记忆”分区，可以搜索、按标签筛选、查看正文与来源、编辑或删除。
3. **使用记忆**：新对话里直接提问即可。助手会按需取回相关记忆，不需要你重复粘贴。

示例说法：

- “记住：这个项目默认用 pnpm，不要用 npm。”
- “以后回答我先给结论，再给理由。”
- “记住项目代号是 Kestrel，发布窗口是周五上午。”
- “这条只对当前对话有效，不要带到其他对话。”

## 4. 特色功能

### 4.1 新对话不再从零开始：跨对话记忆

默认保存的记忆是“共享”的：同一记忆分组内的新对话都能取回。适合偏好、项目约定这类跨对话仍然成立的内容。

如果某条内容只适合当前对话，保存时说明“只记住当前对话”，它会变为“私有”：只有当前对话能读写，其他对话看不到；本机设置页的管理员仍可查看和清理。

### 4.2 压缩不会丢掉你刚说的话：最近 5 个真人回合保护

对话变长需要压缩时，最近 5 个“你亲自发出的回合”不会被压缩或改写；长回合里的工具输出也默认受到保护。

这样做的目的，是让助手在长任务中始终保留你最近的需求、纠正和决定，不会因为早期内容被压缩而“忘记刚才说过的要求”。

### 4.3 先确认记住，再压缩

上下文接近上限时，助手不会立刻丢弃历史，而是先确认这段对话里的关键内容是否已经保存成记忆、之后是否还能取回。

- 如果到了必须压缩的程度、但关键内容还没保存，助手会收到一次提醒，让你先保存关键约定；
- 如果条件不满足，压缩会先推迟；连续推迟到上限或上下文非常紧张时，才会强制压缩；
- 无论哪种情况，最近 5 个真人回合都受保护。

### 4.4 记忆不会越存越乱：整理建议

新记忆和旧记忆相似或矛盾时，插件会给出“合并”或“冲突”建议，例如：

- 两条内容高度相似，建议合并成一条；
- 两条内容一正一反，建议确认哪条仍然有效。

建议只作为提醒，不会自动覆盖你的记忆。你或助手确认后，才会生成一条新的合并记忆，旧内容仍可追溯。

### 4.5 看得见、改得动：记忆浏览器

在 DSH 设置页的“记忆”分区，可以：

- 搜索记忆、按标签筛选；
- 查看正文、标签、重要程度、有效期、来源对话；
- 查看这条记忆的变更记录；
- 编辑（保留历史，不覆盖旧内容）；
- 删除（保留删除记录，便于追溯）。

### 4.6 换个说法也能找到：可选语义检索

默认使用关键词检索，零配置即可用。

开启语义检索后，即使你换了说法、用了同义词，也能找回相关记忆。例如记忆里写的是“数据库迁移只能在周四凌晨”，你问“改表安排在什么时候”，也能命中。

语义检索需要一个兼容 OpenAI embeddings 接口的服务，可以是本地服务，也可以是远端服务。任何一次检索失败都会自动退回关键词检索，不会让对话卡住。

### 4.7 多个助手不互相污染：共享与可见范围

同一 DSH 配置下的多个助手可以共享记忆，但每条记忆有可见范围：

- **共享**：同组助手都能读，只有保存它的对话能改；
- **私有**：只有保存它的对话能读写；
- **开放**：同组助手都能读、都能改（保存时显式指定）。

如果你希望不同项目、不同助手的记忆互相隔离，可以给它们设置不同的“记忆分组”。分组隔离对助手生效；本机设置页的管理员仍可查看全部记忆。

### 4.8 数据在你自己手里：本地保存

记忆保存在本机，不依赖云端账号。你可以通过设置里的保存位置找到它，按需备份或迁移。

开启语义检索时，记忆正文会发送到你配置的检索服务；除此之外，记忆不会自动上传。

### 4.9 轻量、省空间、不挑机器

- **记忆就是一个本地文件，现在约 41 KB**：备份、迁移就是复制这一个文件。
- **没有常驻后台进程**：只在保存、召回、压缩时工作，平时不空转；能跑 DSH 的普通电脑就够用。
- **存的是结构化事实，不是整段对话**：比向量库、图谱或全量会话存档更省空间。
- **压缩力度由模型决定**：插件负责在合适时机触发、保护重要内容、全程可审计，不承诺固定压缩率。

## 5. 设置说明

所有设置都在 DSH 设置页的插件配置中，修改后即时生效。默认值适合大多数用户，不建议一次改很多项。

### 5.1 压缩与保护

| 设置 | 默认 | 作用 | 建议 |
|---|---:|---|---|
| 保护回合数 | 5 | 最近多少个“你亲自发出的回合”不参与压缩 | 保持 5；不建议低于 3 |
| 保护工具结果 | 开启 | 保护区内较长的工具输出是否保持原样 | 保持开启 |
| 软阈值 | 80% | 上下文用到该比例时，开始评估是否压缩 | 一般不用改 |
| 硬阈值 | 92% | 用到该比例时，即使记忆条件不满足也会压缩 | 一般不用改；调低会更早压缩 |
| 连续推迟上限 | 3 | 条件不满足时最多推迟几次，之后强制压缩 | 一般不用改 |
| 预留空间比例 | 0.0625 | 为摘要和波动预留的空间，按上下文窗口比例随模型大小自适应（`headroomTokens` 置 >0 可覆盖为绝对值） | 一般不用改 |
| 提醒方式 | 只在保存时 | “只在保存时”表示不主动打扰；“发现候选时提醒”会在可能值得记的内容出现后提醒一次 | 怕漏记可选提醒 |
| 记忆摘要详细度 | 标准 | 设置页/提示中记忆摘要展示多少触发词 | 标准即可 |

### 5.2 检索

| 设置 | 默认 | 作用 | 建议 |
|---|---|---|---|
| 检索模式 | 关键词 | 关键词检索零配置；混合检索会同时使用语义相似度 | 需要同义改写召回时再开 |
| 语义服务地址 | 空 | 兼容 OpenAI embeddings 的服务地址 | 本地服务示例：`http://127.0.0.1:1234/v1` |
| 语义模型 | 空 | 该服务上的 embeddings 模型名 | 填服务实际提供的模型 |
| 语义服务密钥变量 | 空 | 存放密钥的环境变量名；本地服务可留空 | 不要把密钥直接写进配置 |
| 语义权重 | 0.5 | 混合检索中语义结果的相对权重 | 0.3–0.7 之间调整 |

> 开启语义检索前，请确认你信任该服务：记忆正文会作为检索请求的一部分发送过去。

### 5.3 整理与时效

| 设置 | 默认 | 作用 | 建议 |
|---|---|---|---|
| 整理建议 | 开启 | 写入后给出合并/冲突建议；只建议，不自动修改 | 保持开启 |
| 时间衰减 | 90 天 | 越久未使用的记忆，排序权重逐渐降低；0 表示关闭 | 长期项目可调大或关闭 |

单条记忆还可以设置：

- **重要程度 1–5**：5 表示必须遵守的约束，3 表示普通约定；
- **有效期**：到期后自动退出默认召回，但不会被删除，仍可在设置页查看。

### 5.4 共享与保存

| 设置 | 默认 | 作用 | 建议 |
|---|---|---|---|
| 记忆分组 | default | 给记忆分组；不同分组默认互不可见 | 按项目/用途分组时修改 |
| 默认可见范围 | 共享 | 新记忆默认“共享”还是“私有” | 个人偏好用共享；敏感上下文用私有 |
| 单写者保护 | 开启 | 防止多个 DSH 同时写同一份记忆；第二个实例会变为只读 | 保持开启 |
| 保存位置 | 空 | 自定义记忆保存位置；留空使用默认位置 | 需要备份/迁移时修改 |

> 更改“记忆分组”后，旧记忆仍在设置页可见，但助手默认只读取当前分组；更改“保存位置”后，旧位置的记忆不会自动迁移，请先备份再手动处理。

## 6. 常见问题

**新对话记不住，怎么办？**

按顺序检查：

1. 这条记忆是否真的保存成功（设置页能搜到）；
2. 它的可见范围是否为“私有”（私有只对保存它的对话可见）；
3. 当前对话的记忆分组是否与保存时一致；
4. 是否开启了语义检索但服务不可用（此时会退回关键词检索，可能找不到同义说法）。

**为什么没有自动压缩？**

压缩只在上下文接近上限时发生，而且会先确认关键内容已记住。如果条件不满足，会先提醒或推迟；不是每轮都压缩。

**为什么另一个 DSH 窗口只能看、不能改？**

“单写者保护”开启时，同一份记忆同时只允许一个 DSH 写入；第二个实例会自动变为只读，避免同时写入造成冲突。关闭另一个实例后重启即可恢复写入。

**记忆太多、重复怎么办？**

让助手查看“整理建议”，确认合并或忽略。也可以在设置页手动编辑或删除。

**审计日志会越积越大吗？**

会，但超过约 50 MB 后，最旧的约 40% 审计会自动整理到旁边的归档目录，主文件保留约 60% 热读；查看历史仍能跨归档追溯。特别重要的决策可以让助手用“永久保留”标记，不参与自动整理。记忆正文不会被归档，检索不受影响。

**如何备份？**

在设置中查看或指定“保存位置”。若使用默认位置，请按 DSH 的数据目录备份记忆文件；如果旁边有 `.archive` 目录，也要一起备份，否则会丢失已归档的审计。修改保存位置前，先备份旧文件，避免新旧位置不一致。

**支持多台设备/团队共享吗？**

默认不支持自动同步，也不提供账号、角色和远程权限。多助手共享是本机范围内的可见范围控制，不是多用户权限系统。

**可以存密码或 API Key 吗？**

不建议。请使用专门的密钥管理方式；记忆内容可能被助手读取，开启语义检索时还会发送到你配置的检索服务。

### 如果你只想做三件事

1. 先把最常用的一条偏好和一条项目约定说明白，让助手保存；
2. 保持“整理建议”开启，看到合并/冲突提示时确认一下；
3. 每周花一分钟打开记忆页，删掉过时内容，改掉不再准确的约定。

## 7. 使用边界

- 它是长期记忆，不是文档库：不要用它保存大段原文或完整代码；
- 它不会替代你的判断：重要决定请自己确认；
- 它不保证记住所有内容：只保存明确、稳定、以后仍有用的事实；
- 可见范围是使用上的隔离，不是对抗本机其他用户的安全边界。

# dsh-memory-curate User Guide (English)

- Applies to: 0.3.x
- Audience: everyday users of DeepSeek Harness (DSH) who want long-term memory
- Scope: features, usage, settings and FAQ. This guide intentionally omits implementation details.

> The Chinese guide above is the primary version; this English section mirrors it.

## Before you start: problems you may already know

If you have used an assistant with "memory", these complaints may sound familiar. They are not isolated cases: public discussions about memory products keep returning to lost context across chats, compaction dropping details, memory clutter, lack of control, privacy, and setup complexity. The table maps each complaint to what this plugin does about it.

| Common problem | What this plugin does |
|---|---|
| A new chat forgets my preferences and conventions | Memories are shared across conversations by default; a new chat starts with a lightweight memory summary and pulls the full text on demand |
| After a long chat or compaction, it forgets what I just asked | The last five turns **you personally sent** are protected; compaction first checks that key content has been remembered |
| Memories pile up as duplicates, contradictions and stale facts | A duplicate warning at save time; merge/conflict suggestions after a write; importance and expiry per memory |
| I cannot see what it remembered, or change it | Settings lets you search, inspect sources and change history, edit and delete memories |
| I worry about memories being uploaded or seen by the wrong people | Memories stay on this machine by default; semantic search is optional and explicitly discloses what is sent to the configured service |
| Several assistants or projects bleed into each other | Memory groups plus shared / private / open visibility |
| Setup is too complicated to get started | Zero-config keyword search works out of the box; advanced options are opt-in |

In one sentence: **a long-term memory plugin that does not forget across chats and does not lose what you just said when context is compacted**, while keeping "what is remembered, who can see it, and how to change it" under your control.

## 1. What it is

`dsh-memory-curate` is a long-term memory plugin. It lets the assistant remember your preferences, conventions, project facts and settled decisions across conversations, and it protects the most recent part of a long conversation when context has to be compacted.

It does three things:

- keeps a new chat connected: preferences, conventions and project facts do not need to be repeated;
- keeps compaction from dropping what matters: your latest requests survive;
- keeps memory manageable: duplicates, stale facts and contradictions can be seen, edited and cleaned up.

## 2. What to remember — and what not to

Good candidates:

- long-term preferences: language, answer style, tools, working habits;
- stable conventions: default commands, workflows, naming rules;
- project facts: project codename, module responsibilities, release windows, constraints;
- settled decisions and the reasons behind them;
- time-bound facts such as "use the temporary plan until Friday".

Poor candidates:

- passwords, API keys, tokens and other credentials;
- large raw logs, complete code files or one-off links;
- temporary state that changes constantly (unless you set an expiry);
- anything you do not want to leave this machine (with semantic search enabled, memory text is sent to the retrieval service you configure).

### Who it is especially for

- People running projects across days or weeks who are tired of re-explaining the background;
- People using several assistants or projects who need their memories kept apart;
- Anyone who has been burned by "it forgot after a long chat" or "compaction dropped what I just asked";
- People who want their data on their own machine and their memories visible and editable;
- People who want something that works out of the box, not another memory system to configure.

## 3. Quick start

1. **Save a memory**: say "remember...", "from now on...", or "the convention for this project is...". The assistant decides whether it is worth keeping; you can also ask it to save the current item as long-term memory.
2. **Review memories**: open DSH Settings and find the Memory section. You can search, filter by tag, inspect the text and source, edit or delete.
3. **Use memories**: just ask in a new conversation. The assistant retrieves relevant memories on demand; you do not need to paste old context again.

Example requests:

- "Remember: this project uses pnpm by default, not npm."
- "From now on, give me the conclusion first, then the reasoning."
- "Remember the project codename is Kestrel and the release window is Friday morning."
- "Keep this only for the current conversation; do not carry it into other chats."

## 4. Highlights

### 4.1 Start every chat with context: cross-conversation memory

By default a saved memory is **shared**: new conversations in the same memory group can retrieve it. This suits preferences and project conventions that remain true over time.

If something only makes sense in the current conversation, say so when saving; it becomes **private**. Only that conversation can read or edit it; other conversations cannot see it. The local Settings page administrator can still inspect and clean it up.

### 4.2 Compaction does not drop what you just said: last five human turns

When a long conversation has to be compacted, the last five turns **you personally sent** are not compacted or rewritten. Tool output inside a long turn is protected by default as well.

The goal is continuity: the assistant keeps your latest requests, corrections and decisions even when earlier material is condensed.

### 4.3 Remember first, compact later

When context approaches its limit, the assistant does not immediately discard history. It first checks whether the key content from that part of the conversation has already been saved as memory and can still be retrieved.

- If compaction is unavoidable but the key content has not been saved, the assistant receives one reminder so you can save it first.
- If the conditions are not met, compaction is postponed. It is forced only after repeated postponements or when context is very tight.
- In every case, the last five human turns remain protected.

### 4.4 Keep memories from turning into clutter: consolidation suggestions

When a new memory is similar to, or contradicts, an existing one, the plugin proposes a **merge** or **conflict** resolution. For example:

- two memories say almost the same thing — merge them;
- two memories say opposite things — confirm which one is still valid.

Suggestions are proposals only. Nothing is overwritten automatically. When you or the assistant confirms, a new merged memory is created and the old content remains traceable.

### 4.5 See it, change it: memory browser

The Memory section in DSH Settings lets you:

- search memories and filter by tag;
- inspect text, tags, importance, expiry and source conversation;
- view the change history of a memory;
- edit it (history is preserved; the old content is not overwritten);
- delete it (the deletion is recorded and remains traceable).

### 4.6 Find it even when you phrase it differently: optional semantic search

Keyword search is the default and needs no configuration.

With semantic search enabled, memories can be found even when you use different wording or synonyms. For example, a memory saying "database migrations only happen early Thursday" can be found by asking "when can we change the database structure?".

Semantic search needs a service compatible with the OpenAI embeddings interface; it can be local or remote. If a retrieval request fails, the plugin falls back to keyword search automatically, so the conversation does not get stuck.

### 4.7 Share without bleeding into each other: groups and visibility

Multiple assistants under the same DSH setup can share memories, and every memory has a visibility:

- **Shared**: assistants in the same group can read it; only the conversation that saved it can edit it.
- **Private**: only the conversation that saved it can read or edit it.
- **Open**: assistants in the same group can read and edit it (explicitly chosen when saving).

If you want different projects or assistants to stay isolated, give them different **memory groups**. Group isolation applies to assistants; the local Settings page administrator can still see every memory.

### 4.8 Your data stays with you: local storage

Memories are stored on this machine and do not require a cloud account. You can find or set the storage location in Settings and back it up or move it as needed.

With semantic search enabled, memory text is sent to the retrieval service you configure. Otherwise memories are not uploaded automatically.

### 4.9 Light, space-saving, easy on any machine

- **Memories live in a single local file, currently about 41 KB**: backing up or moving them means copying one file.
- **No background daemon**: it works only while saving, recalling or compacting, so an ordinary machine that can run DSH is enough.
- **It stores structured facts, not whole conversations**: more space-efficient than vector stores, graphs or full session archives.
- **Compaction strength depends on the model**: the plugin triggers at the right time, protects what matters and stays fully auditable; it does not promise a fixed compression ratio.

## 5. Settings

All settings live in the plugin configuration on the DSH Settings page and take effect immediately. The defaults work for most users; avoid changing many values at once.

### 5.1 Compaction and protection

| Setting | Default | What it does | Advice |
|---|---:|---|---|
| Protect turns | 5 | How many of your latest human turns are excluded from compaction | Keep 5; do not go below 3 |
| Protect tool results | On | Keep long tool output inside the protected window intact | Keep on |

| Max consecutive deferrals | 3 | How many times compaction may be postponed before it is forced | Usually leave unchanged |

| Capture mode | Only on save | "Only on save" never interrupts; "Remind on candidates" adds one reminder when something worth remembering appears | Choose reminders if you tend to forget to save |
| Memory summary detail | Standard | How many trigger words appear in the memory summary | Standard is fine |

| Setting | Default | What it does | Advice |
|---|---|---|---|
| Retrieval mode | Keyword | Keyword search needs no setup; Hybrid also uses semantic similarity | Enable Hybrid when paraphrases matter |
| Semantic service URL | Empty | Address of an OpenAI-embeddings-compatible service | Local example: `http://127.0.0.1:1234/v1` |

### 5.3 Organization and time

| Setting | Default | What it does | Advice |
|---|---|---|---|
| Consolidation suggestions | On | Propose merges/conflicts after a write; never changes memories automatically | Keep on |
| Time decay | 90 days | Older, unused memories gradually rank lower; 0 disables decay | Increase or disable for long-lived projects |

Each memory can also carry:

- **Importance 1–5**: 5 means a must-follow constraint, 3 an ordinary convention.
- **Expiry**: after it passes, the memory leaves default recall but is not deleted and remains visible in Settings.

### 5.4 Sharing and storage

| Setting | Default | What it does | Advice |
|---|---|---|---|
| Memory group | default | Groups memories; different groups are invisible to each other by default | Change when separating projects or purposes |
| Default visibility | Shared | Whether new memories are shared or private by default | Shared for preferences; private for sensitive context |

## 6. FAQ

**A new conversation does not remember something. What should I check?**

1. Was the memory actually saved? Search for it in Settings.
2. Is its visibility **private**? Private memories are visible only to the conversation that saved them.
3. Is the current conversation using the same memory group?
4. Is semantic search enabled but unreachable? In that case the plugin falls back to keyword search, which may miss paraphrases.

**Why did compaction not happen automatically?**

Compaction runs only when context is close to its limit, and it first checks that key content has been remembered. If the conditions are not met, it reminds or postpones; it does not run on every turn.

**Why is another DSH window read-only?**

With single-writer protection on, only one DSH instance may write the same memory at a time; a second instance becomes read-only to avoid conflicting writes. Close the other instance and restart to restore writing.

**There are too many or duplicate memories. What can I do?**

Ask the assistant to review consolidation suggestions and confirm merges or dismissals. You can also edit or delete memories in Settings.

**Will the audit log keep growing?**

It grows, but once the active file reaches about 50 MB the oldest ~40% of audits roll into an adjacent archive directory, keeping about 60% hot; history remains traceable across archives. Mark a critical decision as permanently retained to keep it out of the automatic roll. Memory bodies are never archived, so retrieval is unaffected.

**How do I back up memories?**

Check or set the storage location in Settings. If you use the default location, back up the memory file from the DSH data directory. If an `.archive` directory sits next to it, back that up too; otherwise archived audits are lost. Before changing the location, back up the old file so the two locations do not diverge.

**Does it sync across devices or support teams?**

No automatic sync, accounts, roles or remote permissions. Multi-assistant sharing is local visibility control, not a multi-user permission system.

**Can I store passwords or API keys?**

Not recommended. Use a dedicated secret manager. Memories may be read by the assistant, and with semantic search enabled their text is sent to the retrieval service.

### If you only do three things

1. Save one frequently used preference and one project convention first.
2. Keep consolidation suggestions on and confirm merge/conflict prompts when they appear.
3. Spend one minute a week in the Memory page: remove stale items and correct conventions that no longer hold.

## 7. Boundaries

- It is long-term memory, not a document store: do not keep large raw texts or complete code files.
- It does not replace your judgment: confirm important decisions yourself.
- It does not guarantee remembering everything: save only clear, stable facts that will still matter later.
- Visibility is a usage-level separation, not a security boundary against other users of this machine.
